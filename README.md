# SuperBPE Tokenizer — Research Repository

## Abstract
This repository presents my implementation of a **SuperBPE tokenizer** for the Codabench competition. The project builds on standard Byte‑Pair Encoding (BPE) and extends it to **SuperBPE**, where merges may cross whitespace boundaries to capture frequent multi‑word expressions. The tokenizer is designed to be **lossless**, efficient, and reproducible, with all learned assets serialized for evaluation. This repository serves as a research artifact, documenting both the engineering implementation and the methodological context.

## Repository Structure
- `tokenizer.py` — Submission entry point implementing the `Tokenizer` class (lossless encoder/decoder).
- `tokenizer.json` — Example vocabulary generated by the training pipeline.
- `train_tokenizer.py` — Prototype trainer implementing BPE‑style merges for development and debugging.
- `evaluate.py` — Lightweight evaluation script for round‑trip correctness and token statistics.
- `preprocess_text.py` — Reference preprocessing pipeline aligned with competition requirements.
- `debug_corpus.txt` — Small corpus for local debugging.
- `tests/` — Unit tests validating round‑trip fidelity.

## Experimental Workflow
1. **Tokenizer training (development phase):**
   ```bash
   python train_tokenizer.py --input debug_corpus.txt --vocab-size 20000 --repeat 10 --out tokenizer.json
   ```

   Use `--repeat` only for small development corpora; train on the actual target corpus when available.

2. **Evaluation of round‑trip fidelity and token statistics:**
   ```bash
   python evaluate.py --model tokenizer.json --input debug_corpus.txt
   ```

3. **Validation through unit tests:**
   ```bash
   python -m unittest discover -v
   ```

## Design Considerations
The competition requires `tokenizer.py` as the submission entry point, with a `Tokenizer` class implementing `__init__`, `encode`, and `decode`. Encoder and decoder instances are constructed independently; therefore, all learned assets must be serialized (e.g., `tokenizer.json`) and loaded in `__init__`. The baseline implementation is deliberately minimal, serving as a foundation for extending to SuperBPE: frequency‑driven merges that cross whitespace boundaries after a configurable stage, while ensuring exact reversibility.

## Packaging and Submission
Submissions must be packaged as a single archive containing `tokenizer.py` at the root. Optional files (e.g., `tokenizer.json`) may be included, but external dependencies or network access are prohibited. The evaluator does not retrain models; all learned assets must be pre‑packaged.

Use `package_submission.py` to create the submission archive, and `package_full_repo.py` to bundle the repository for sharing or backup.

```bash
python package_submission.py --out submission.zip --model tokenizer.json
python package_full_repo.py --out project_bundle.zip
```

## Submission Criteria
- Vocabulary size ≤ 20,000 distinct tokens.
- Lossless round‑trip encoding/decoding on debug and development corpora.
- End‑to‑end runtime (initialization + encode + decode) ≤ 20 minutes for the 2M‑character evaluation corpus.

## Benchmarking
`benchmark.py` replicates a small corpus to approximate the final evaluation size and measures runtime performance. This enables local estimation of competition runtime constraints.

## Related Work
The design of this tokenizer is inspired by *SuperBPE: Space Travel for Language Models*.

- Standard BPE learns frequent subword units by merging adjacent characters within words.
- SuperBPE extends this by allowing merges across whitespace, enabling representation of frequent multi‑word expressions.
- This approach reduces the number of emitted tokens while maintaining exact reversibility, aligning with broader research on efficient tokenization for large language models.
- Related studies on Byte Pair Encoding, SentencePiece, and tokenization efficiency provide context for the evolution of subword tokenization methods.
